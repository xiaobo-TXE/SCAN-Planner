## 1. 每个新终端先做这一步

```bash
source ~/record_tools/env.sh
```

会打印 `[env] 已就绪 ROS_DOMAIN_ID=0 工作空间已 source`，
等价于 source 了 `/opt/ros/humble` + `~/nav_ws` + `~/scan_planner_github_ws`。

> `record_run.sh` 自己会 source；但 **`analyze_run.py` 需要你先 source**，
> 否则解析不了 `Bspline` / `LocStatus` 这些自定义消息。

## 2. 录前自检

```bash
bash ~/record_tools/record_run.sh --check
```

正常情况下：

- 只有 `/test_event` 不存在（正常，它只在打标注时才发）；
- `/loc/status state: 3`（定位正在跟踪）；
- `/loc/robo/odom` ≈ 10 Hz、`/lio/cloud_world` ≈ 10 Hz、`/cmd_vel` ≈ 100 Hz。

若关键话题缺失，先别录，检查节点是否都起来了。

## 3. 开始录制

### 3.1 前台录（推荐，简单）

```bash
# 精简档（推荐）：只录 定位 / 全局 / 局部 / 速度 + /tf，约 0.1~0.2 MB/s
bash ~/record_tools/record_run.sh run1 --slim --auto-events

# 全量档：含点云/栅格，约 75 MB/s（≈4.5 GB/min），磁盘要够
bash ~/record_tools/record_run.sh run1 --auto-events
```

- **停止**：`Ctrl-C` **只按一次**，等它打印 `完成：/home/unitree/bags/run1_xxx`
- `--auto-events`：控制器"想走不动"时**自动**往 `/test_event` 打 `AUTO:stuck / AUTO:move`

### 3.2 后台录（这个终端还能干别的，SSH 断了也不停）

```bash
setsid bash ~/record_tools/record_run.sh run1 --slim --auto-events \
  > ~/bags/rec_run1.log 2>&1 < /dev/null &

# 停止（任意终端）：
bash ~/record_tools/record_run.sh --stop
```

### 3.3 手动打事件（另开终端，可选）

```bash
bash ~/record_tools/record_run.sh --event "点目标A"
bash ~/record_tools/record_run.sh --event "门口停住"
bash ~/record_tools/record_run.sh --event "拐角卡死"
```

事件会进 `/test_event`，分析时画在"7_事件时间轴"上。

### 3.4 录制中可以查

```bash
du -sh ~/bags/<标签>_<时间戳>     # 包大小是否在增长
bash ~/record_tools/record_run.sh --check     # 话题是否都在
```

## 4. 数据生成在哪

```
~/bags/
├── run1_<时间戳>/                 ← 本次的包（例：run1_20261028_092659）
│   ├── run1_..._0.db3             ← 数据本体
│   ├── metadata.yaml              ← 包元数据（rosbag2 读它）
│   ├── bag_info.txt  meta.yaml    ← 可读摘要 / 标签·时长·话题数
│   ├── analysis/                  ← 【分析后生成】report.md + figs/
│   └── logs_maploc/               ← super_lio 日志（自动收拢）
├── INDEX.md                       ← 录制索引（每次追加一行）
├── rec_run1.log                   ← 录制过程日志
├── auto_events.log                ← 自动卡住标注日志
└── qos_overrides.yaml             ← QoS 覆盖（录制时自动使用）
```

## 5. 分析（录完一条命令，约 1 分钟）

```bash
source ~/record_tools/env.sh
python3 ~/record_tools/analyze_run.py ~/bags/run1_20261028_092659
```

输出到 `~/bags/<包>/analysis/`：

- `report.md`：时长/里程/卡住段/速度差/跟踪误差/定位偏差 + 自动结论
- `figs/`：7 张图（见下）

常用参数：

```bash
--odom-topic /loc/robo/odom   # 换"实际轨迹"来源（默认 /lio/robo/odom，即规划器用的 world 系）
--out <目录>                  # 指定输出目录（默认 <包>/analysis）
--map-frame map --world-frame world   # 若你的坐标系叫别的名字
```

## 6. 七张图说明

| 文件 | 内容 |
|---|---|
| `1_定位轨迹.png` | WORLD 系轨迹（蓝带）vs MAP 系轨迹（橙虚线，经 `/tf` 变到 WORLD） |
| `2_定位偏差.png` | 两定位源偏差（紫实线）+ TF 修正量（青虚线）；偏差恒小、修正量恒定 = 定位一致且不漂 |
| `3_定位状态.png` | `/loc/status.state`（3=跟踪中），掉档一眼可见 |
| `4_定位rmse.png` | 激光帧与先验地图的匹配残差 |
| `5_轨迹对比.png` | **5a 俯视**：全局（紫虚线）/ 局部（绿，淡显全部+抽样亮显）/ 实际（蓝带）；**5b 高度 z 随时间**：实际 / 局部规划 / 全局规划 |
| `6_速度对比.png` | **三个子图 vx / vy / wz**，每张都是 **下发(cmd_vel) vs 实际(odom)** |
| `7_事件时间轴.png` | 卡住段 / 冻结段 / 事件标注（黄=手动、绿=自动） |

**配色约定**：蓝=实际/实测、橙=地图定位、紫=全局轨迹/偏差、绿=局部轨迹、红=下发指令/卡住、青=TF 修正量/定位状态。
实线=实际量，虚线=参考/派生量；图例自动放到最空的角。

## 9. 注意事项 / 常见问题

| 现象 | 原因 / 处理 |
|---|---|
| 包特别大 | 全量档 ≈4.5 GB/min。日常用 `--slim`；或加 `--compress`（但见下条） |
| 分析报"读不了 / file is not a database" | 用了 `--compress`（file 压缩）。先解压：`zstd -d -f x.db3.zstd -o x.db3 && rm x.db3.zstd`，并把 `metadata.yaml` 的 `compression_mode: FILE` 改成 `NONE` |
| 停止后没出现 `完成：…` | 等一会儿（大包收尾/压缩要几分钟）；**不要 `kill -9`** |
| 分析时定位图为空 | 包里没有 `/tf` → 下次务必用 `--slim`（已含 `/tf`）或全量档 |
| 分析报缺自定义类型 | 没 source 工作空间 → `source ~/record_tools/env.sh` |
| 磁盘不够 | `df -h ~`；删旧的 `~/bags/run*` 包 |

## 10. 一句话流程

```
source ~/record_tools/env.sh
→ record_run.sh --check                     # 自检
→ record_run.sh run1 --slim --auto-events   # 开录
→ 发目标点 / 跑路线 / 打事件
→ Ctrl-C 一次                               # 停止并自动归档
→ python3 analyze_run.py ~/bags/<包>        # 分析出 7 张图
→ 打开 ~/bags/<包>/analysis/figs/ 查看
```
